# EFI Visual System

## Core rule

Treat the EFI visual system as a reusable publication interface, not decoration.

Preserve the underlying technical meaning exactly. Change presentation, hierarchy, composition, and visual grammar only when doing so does not inflate, weaken, or alter a technical claim, proof boundary, status, authority boundary, or patent/legal statement.

## Source order

1. If the current Xxaion-Labs/EFI repository is accessible, read these canonical public sources first:
   - docs/VISUAL-SYSTEM.md
   - site/DESIGN-TOKENS.json
   - site/VISUAL-GRAMMAR.json
   - assets/UI-ASSET-MAP.md
2. Use the repository state as CURRENT visual truth.
3. If the repository is unavailable, use this Skill's bundled references as the fallback snapshot.
4. Never invent a rival brand system because a surface is inconvenient. Adapt density instead.

## Invariant calling card

Every public EFI surface should carry enough of these signals to be recognizable without a logo wall:

- void-black field or black-dominant negative space;
- acid-green identity/current-state signal;
- spectral secondary energy chosen by semantic role;
- technical rail, divider, node, orbit, or sigil geometry;
- disciplined uppercase micro-labels or instrument-style metadata where appropriate;
- explicit proof/status vocabulary when the content makes claims;
- one clear EFI identity mark on major public surfaces.

Color is energy, not wallpaper.

## Semantic color roles

Use color by meaning:

- Acid Green #A8FF00: EFI identity, CURRENT, active field, primary action.
- Electric Violet #A855FF: relation, shared field, secondary cognition.
- Molten Orange #FF8A00: EFFECT, materialization, warning edge, live transition.
- Hot Magenta #FF00E6: experiment, exception, unstable possibility, high-energy emphasis.
- Cyan #00D4FF: observation, signal, world contact, evidence ingress.
- Void Black #050505: canvas, silence, negative space.

Do not rainbow-fill entire surfaces. Use one dominant signal plus limited secondary accents.

## Density profiles

### REDUCED
Use for README sections, source repositories, CLI output, code comments, compact Skill UI, issue templates, and small technical artifacts.

### STANDARD
Use for GitHub Pages, technical docs, public reports, release notes, dashboards, and ordinary EFI presentations.

### FULL
Use for launch surfaces, hero graphics, major white-paper covers, keynote/title slides, posters, campaign art, and social hero images.

Read references/surface-recipes.md when the output medium is GitHub, document/PDF, slides, social graphics, Skill UI, or CLI/terminal.

Read references/brand-contract.md when selecting colors, motifs, hierarchy, state labels, or QA criteria.

## Claims and proof

Never use visual intensity to imply a stronger technical claim than the source supports.

Preserve exact distinctions such as CURRENT, OPEN, PROVED within a declared boundary, NOT CLAIMED, ATTRACTOR, and ACTIVE DEVELOPMENT.

Do not turn an attractor into a present achievement or a bounded proof into an unrestricted capability claim.

## Composition laws

- One visual center per section.
- Use rings for continuity/identity, orbits for relations, rails for transitions, and nodes for state/evidence.
- Frames contain meaningful content. Do not scatter frame fragments as stickers.
- Reuse existing canonical assets before generating new artwork.
- Use technical typography and spacing, but keep body text readable.
- Keep status and evidence surfaces instrument-like, not marketing-like.
- Preserve accessibility: contrast, alt text, legibility, reduced motion, semantic structure.
- Prefer content density over decorative density.

## Quality gate

Before delivering a public EFI artifact, verify:

1. It is recognizable as EFI without relying only on the letters EFI.
2. Color roles are semantic, not random.
3. There is no generic blue-gradient AI styling.
4. There is no random cyberpunk decoration detached from content.
5. The strongest visual emphasis matches the strongest actual claim.
6. Proof/status boundaries remain explicit.
7. The surface is readable on its intended device and at its intended scale.
8. Existing canonical assets were reused when suitable.
9. The density profile matches the medium.
10. The artifact feels like another projection of one living system, not a one-off theme.
